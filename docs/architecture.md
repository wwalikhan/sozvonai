# Архитектура SozvonAI

Этот документ фиксирует все ключевые технические решения по MVP до начала кодирования. Цель — чтобы реализация шла по готовому плану, без архитектурных развилок на ходу.

---

## 1. Обзор пайплайна

```
Источник звука ──▶ VAD/чанкинг ──▶ Потоковая ASR (faster-whisper) ──▶ Live-диаризация (грубая) ──▶ UI (текст появляется по ходу звонка)
                                                                              │
                                                                              ▼ (после завершения звонка)
                                                                   Offline-диаризация (pyannote, точная)
                                                                              │
                                                                              ▼
                                                                  Реконсиляция → финальный транскрипт → хранилище
```

Ключевая идея: во время звонка пользователь видит текст с приблизительными метками "Спикер 1 / Спикер 2" почти в реальном времени. Сразу после звонка фоновая задача пересчитывает диаризацию точной моделью по всей записи целиком и заменяет черновые метки на выверенные. Это осознанный компромисс: точная диаризация требует глобального контекста всей записи и не работает по кускам "на лету" — попытка сделать её live-точной так же, как whisper live-транскрипцию, была бы избыточным риском для MVP.

## 2. Источники аудио

### 2.1 Очная встреча (диктофон/микрофон ноутбука)
Простой случай: один микрофон пишет всех участников в комнате. Захват через браузер (`getUserMedia`) — работает "из коробки" для live-режима.

### 2.2 Онлайн-звонок (Zoom / Google Meet / Teams)
Микрофон пользователя не слышит собеседника — нужен захват звука другой стороны. Два пути:

- **Live (MVP)**: захват аудио вкладки браузера через `getDisplayMedia({audio: true, video: false})` — пользователь делится звуком вкладки со звонком, плюс отдельно захватывается свой микрофон. Оба потока микшируются через Web Audio API и стримятся вместе. Работает в Chrome/Edge без установки доп. ПО.
- **Batch (запасной путь)**: пользователь скачивает готовую запись звонка из Zoom/Meet/Teams и загружает файл в сервис после встречи. Не требует захвата звука вживую.

### 2.3 Загрузка готового файла (универсальный fallback)
Просто загрузка аудио/видео файла (mp3/wav/m4a/mp4) — работает всегда, независимо от источника записи. Видео проходит через `ffmpeg` для извлечения аудиодорожки.

## 3. Обработка звука

### 3.1 VAD и чанкинг
`silero-vad` режет входящий поток на речевые сегменты (по паузам), а не на произвольные тайм-слайсы — это даёт границы фраз, а не рваные куски слов. Буфер накапливает ~3-6 сек речи перед отправкой в ASR.

### 3.2 Потоковая транскрибация
`faster-whisper` (CTranslate2, CPU, int8-квантизация) — каждый речевой чанк транскрибируется по мере поступления, результат уходит в UI через WebSocket как частичный/финальный сегмент.

- Модель по умолчанию: **small** (баланс скорости/качества на CPU для русского языка).
- Конфигурируемый fallback на **base**, если whisper не успевает за темпом речи на слабом железе (см. §8).
- Язык: `ru` по умолчанию, с возможностью auto-detect.

### 3.3 Диаризация — гибридный подход
- **Live (черновая)**: на каждом VAD-сегменте считается голосовой эмбеддинг (`speechbrain`/`resemblyzer`), онлайн-кластеризация против спикеров, уже встреченных в этом звонке → метки "Спикер 1/2/3" по ходу разговора. Точность ограничена — это ожидаемо.
- **Offline (точная)**: после завершения звонка `pyannote.audio` прогоняется по полной записи и строит финальную, куда более надёжную разметку спикеров.
- **Реконсиляция**: финальные метки спикеров накладываются на уже готовый текст (текст из live ASR не пересчитывается — меняются только ярлыки говорящих), результат сохраняется как окончательная версия транскрипта.

## 4. Модель данных

Сущности:

- **Call** — id, title, source (mic / tab_capture / upload), status (recording / processing / done / failed), error (причина, если failed), duration_sec, created_at. Путь к аудиофайлу — не поле Call, а отдельная связанная таблица AudioFile.
- **Speaker** — id, call_id, display_name ("Спикер N", позже — переименовывается пользователем вручную).
- **TranscriptSegment** — id, call_id, speaker_id (nullable — не удалось сопоставить с диаризацией), start_ms, end_ms, text, is_final (0 — черновой live-сегмент, 1 — финальный после реконсиляции или batch).
- **AudioFile** — call_id (1:1 с Call), путь на диске, формат, размер в байтах.

Хранение метаданных — **SQLite** (один файл, без отдельного сервера БД — согласуется с «без базы знаний», это просто структурированное хранилище, а не смысловая KB). Сами аудиофайлы — на диске в `storage/calls/{call_id}/audio.wav`.

## 5. Backend-архитектура (FastAPI)

- `WS /ws/stream/{call_id}` — приём аудиочанков от фронтенда в реальном времени, отправка обратно частичных транскриптов.
- `POST /calls/upload` — batch-загрузка готового файла.
- `GET /calls` — список звонков.
- `GET /calls/{call_id}` — метаданные + транскрипт.
- `GET /calls/{call_id}/export?format=txt|pdf` — экспорт.
- Фоновая задача (`asyncio` background task, без Celery/Redis — не нужно для однопользовательского локального MVP) запускается по завершении звонка: точная диаризация → реконсиляция → пометка call как `done`.

---

## 6. Frontend-архитектура

Минимальный SPA (может быть на чистом JS для MVP, без тяжёлого фреймворка):

1. **Страница звонка (live)** — кнопки "Начать/Остановить", захват mic (+ вкладки при online-звонке), микширование через Web Audio API, отправка чанков по WebSocket, отрисовка текста по мере поступления с метками спикеров.
2. **Страница загрузки файла** — drag & drop, статус обработки (processing → done).
3. **Список звонков** — история с датами/статусами.
4. **Просмотр транскрипта** — финальный текст по спикерам, кнопка экспорта, возможность переименовать "Спикер 1" → реальное имя.

## 7. Технологический стек (финал)

| Компонент | Выбор | Примечание |
|---|---|---|
| Backend | Python 3.11 + FastAPI | Отдельное окружение `backend/.venv`, не путать с `tools/claude-memory-compiler` (там Python 3.14 через uv — независимый инструмент) |
| ASR | faster-whisper (small, GPU/CUDA, fp16) | Ключевое требование — без платных API. Бэкенд инференса конфигурируется (`device: cuda\|cpu`), CPU int8 остаётся как fallback |
| VAD | silero-vad | Лёгкая, CPU достаточно (не узкое место) |
| Live-диаризация | speechbrain/resemblyzer эмбеддинги + онлайн-кластеризация | Грубая, для live-UX, CPU достаточно |
| Offline-диаризация | pyannote.audio | Точная, torch с CUDA — на порядок быстрее CPU-режима |
| Аудио-конвертация | ffmpeg | Извлечение звука из видеозаписей |
| Хранилище метаданных | SQLite | Файловая БД, без сервера |
| Хранилище аудио | Локальный диск (`storage/`) | Путь конфигурируется |
| Real-time транспорт | WebSocket | Между браузером и FastAPI |
| Frontend | Vanilla JS / лёгкий фреймворк | Web Audio API для захвата и микширования |

## 8. Производительность на GPU (CUDA)

Целевая машина имеет дискретную NVIDIA GPU (GTX 1650, 4GB VRAM) — этого достаточно для `faster-whisper small` и `pyannote.audio` одновременно.

- `faster-whisper small` на GPU (fp16/CUDA) — near-realtime фактор в разы лучше 1x (минута записи обрабатывается за секунды, не за минуту), с большим запасом по задержке для live-режима.
- Offline pyannote-проход на CUDA — на порядок быстрее CPU-режима, но всё равно выполняется в фоне после звонка, не блокирует UX.
- Бэкенд инференса (`device: cuda|cpu`) конфигурируется в `.env`/`config.py` — CPU-режим (int8, модель `small` с откатом на `base`) остаётся рабочим fallback-путём для машин без GPU (важно для будущего деплоя на сервер/облако — там GPU может не быть).
- VAD и live-диаризационные эмбеддинги — лёгкие, CPU для них достаточен в любом случае, не переводим на GPU без необходимости.
- Требуется установка CUDA-совместимых сборок зависимостей (`torch`+cu, `ctranslate2` с CUDA-поддержкой) — тяжелее по объёму, чем чистый CPU int8-путь, но ставится один раз при настройке окружения.

## 9. Хранение и приватность

- Всё локально по умолчанию — никаких внешних сервисов транскрибации.
- Аудиофайлы хранятся на диске (нужны для offline-диаризации и возможной пересборки); политика удаления/ретенции — на усмотрение пользователя позже, в MVP не автоматизируем.
- `.gitignore` уже исключает `uploads/`, `models/`, аудиоформаты — сырые данные и веса моделей не попадают в git.

## 10. Обработка ошибок и edge-кейсы

- Отказ в доступе к микрофону/вкладке — понятная ошибка в UI, предложение fallback на загрузку файла.
- Обрыв WebSocket во время звонка — переподключение с продолжением сессии (буфер на клиенте не теряется, дозаписывается на сервере).
- Долгая тишина — VAD просто не шлёт чанки, коннект не рвём.
- Речь не на русском — whisper справится за счёт мультиязычности модели, но качество вне ru не гарантируется в MVP (auto-detect как опция).
- Перекрывающаяся речь (оба говорят одновременно) — известное слабое место диаризации, не решается в MVP, отдаём как есть.
- Один активный звонок за раз в live-режиме на MVP — многопоточная поддержка нескольких одновременных живых звонков выносится за рамки MVP.

## 11. Поэтапный план реализации

Реализовывать в этом порядке — каждая стадия самостоятельно проверяема и снижает риск перед следующей:

**Stage 0 — Скелет**
Структура `backend/`, FastAPI + `uvicorn` поднимается, `ffmpeg`/зависимости проверены.

**Stage 1 — Batch-пайплайн (ядро качества)**
Загрузка готового файла → `faster-whisper` (не потоково) → `pyannote` офлайн-диаризация → сохранение в SQLite → просмотр транскрипта в UI. Это проверяет качество ASR и диаризации в самом простом виде, без сложности стриминга.

**Stage 2 — Live-транскрибация с микрофона (очные встречи)**
VAD-чанкинг + потоковый `faster-whisper` + WebSocket + грубая live-диаризация + UI с текстом по ходу разговора.

**Stage 3 — Live-захват онлайн-звонков**
Захват аудио вкладки браузера (`getDisplayMedia`) + микширование с микрофоном → тот же live-пайплайн из Stage 2.

**Stage 4 — Реконсиляция и полировка**
Фоновая точная диаризация после звонка, замена черновых меток, экспорт (txt/pdf), список звонков, переименование спикеров.

---

## 12. Осознанно отложено за рамки MVP

- Аутентификация / multi-user — сейчас однопользовательский локальный инструмент.
- Выбор платформы деплоя — решается после того, как пайплайн проверен локально.
- AI-саммари звонка через LLM — отдельная фича на будущее, не противоречит "без базы знаний" (это не RAG), но не нужна для ядра MVP.
- Несколько одновременных live-звонков.
- Точная диаризация перекрывающейся речи.
