# Проблемы и баги

Записывай сюда обнаруженные проблемы, баги и блокеры по мере работы над проектом. Формат: дата — описание — статус (открыто/решено).

- 2026-09-25 — `POST /ws/stream` всегда писал `source="mic"` в БД независимо от режима звонка на фронтенде. — **решено** (2026-09-25, Stage 4): `live.html` передаёт режим как query-параметр WS (`?source=mic|tab_capture`), `main.py: stream_call` читает его и сохраняет в `Call.source`.
- 2026-09-25 — PDF-экспорт (`backend/app/main.py: _build_pdf`, `fpdf2` + системный TTF) визуально корректно рендерит кириллицу (проверено в Chromium), но `pdftotext` (poppler) не извлекает кириллический текст из результата — вероятно, проблема `/ToUnicode` CMap встроенного шрифта fpdf2. Не блокирует использование (PDF читается глазами, печатается), но ограничивает copy/paste и полнотекстовый поиск по экспортированным PDF. — **закрыто как false positive** (2026-09-26): побайтово разобрал сгенерированный PDF вручную (CID-коды, `/ToUnicode` CMap, PDF-эскейпинг литеральных строк) — кодировка полностью соответствует спецификации, все байты декодируются в исходный текст без потерь. Проверил на минимальном примере и на стресс-тесте (весь кириллический алфавит верхний/нижний регистр + цифры + пунктуация) двумя независимыми движками: PyMuPDF и pypdfium2 (тот же движок, что в Chrome/Edge, — то, чем реально пользуются люди для просмотра/копирования PDF) — оба извлекли текст побайтово идеально. `pdftotext`, который не сработал, оказался не poppler, а xpdf-сборка (`pdftotext.exe` из Git Bash/mingw64, версия "4.06 [www.xpdfreader.com]") — видимо, изначальная проверка была на нём, и вывод "poppler не работает" был ошибочным из-за путаницы инструментов с одинаковым именем команды. Правки в `_build_pdf` не потребовались.
- 2026-09-25 — После снижения `ASR_LIVE_BEAM_SIZE` до 1 (см. запись ниже про нагрев GPU) в реальном live-звонке (Stage 3 тест) замечены явно ошибочные распознавания на речи пользователя в микрофон ("Чертозавис.", "Палин." — бессмысленные слова, вероятно на фоне шума/тихой речи). Не проверено A/B против beam_size=5 на том же аудио — возможно, совпадение (шумный сегмент), а не следствие greedy-декодирования. Если подобные искажения будут повторяться — рассмотреть возврат `ASR_LIVE_BEAM_SIZE` на 2-3 как компромисс между нагревом и точностью. — открыто, для наблюдения.
- 2026-09-25 — Сильный нагрев GPU (~70°C) во время live-звонков. Обсудили замену локального Whisper на платный Gemini API — отклонено пользователем, т.к. напрямую противоречит зафиксированному решению "только локальный Whisper, без платных API транскрибации" (privacy/офлайн-режим/стоимость). Вместо этого снижен beam_size для live-пути ASR: `app/config.py: ASR_LIVE_BEAM_SIZE` (default 1, greedy) отдельно от batch (`ASR_BATCH_BEAM_SIZE`, default 5) — live-транскрибация вызывается почти непрерывно на каждый VAD-сегмент, а beam_size прямо пропорционален GPU-нагрузке. Если тепло всё ещё некомфортно — дополнительно можно ограничить power limit видеокарты (`nvidia-smi -pl <watts>`, системная настройка вне кода приложения) или понизить `ASR_MODEL_SIZE` до `base` в `.env`. — решено (частично, в рамках допустимого без пересмотра архитектуры).
- 2026-09-25 — Известная галлюцинация faster-whisper на паузах/тихих участках: модель иногда вместо тишины выдаёт текст вида "Редактор субтитров Н.Закомолдина" / "Корректор А.Егорова" (артефакт обучающих данных — субтитры с YouTube). Впервые замечено QA на синтетике (Stage 4 тест, короткий 128мс сегмент), подтвердилось на реальном живом голосе пользователя (live-звонок, mic-режим, сегмент на 21954мс после паузы). Открытая проблема faster-whisper "small", не специфична для проекта — при желании митигировать можно порогом `no_speech_prob`/`compression_ratio` в `app/asr.py` или явным списком известных фраз-галлюцинаций для фильтрации. — открыто, средний приоритет (искажает транскрипт для делового звонка).
- 2026-09-26 — Live-диаризация на реальной речи (не TTS) давала грубые ошибки, не проявлявшиеся на синтетике: (1) при быстрой смене говорящих без паузы ≥700мс `SpeechChunker` (`app/vad.py`) склеивал реплики РАЗНЫХ спикеров в один сегмент длиной до 18с — один эмбеддинг на сегмент с двумя голосами неизбежно даёт один ярлык; тот же порог тишины вызывал задержку до 18с перед показом текста на экране; (2) однопороговый (0.75) классификатор в `LiveSpeakerClusterer` (`app/live_diarization.py`) порождал фантомных лишних спикеров на короткие/эмоционально окрашенные сегменты с шумным эмбеддингом; (3) центроид спикера, обновляемый только при уверенном совпадении, навсегда застревал на шумном первом (часто коротком) эмбеддинге — не мог самоисправиться на более длинных последующих репликах того же голоса, и один реальный человек со временем расползался на несколько разных "спикеров". — **решено** (2026-09-26): в `app/vad.py` снижен `min_silence_duration_ms` 700→500 и добавлен потолок `max_segment_duration_ms=5000` с флагом `continues_previous` (сегмент, обрубленный по таймауту, а не по паузе, наследует спикера предыдущего куска вместо переклассификации); в `app/live_diarization.py` введены два порога (0.75 — уверенное совпадение, 0.6 — минимум для нового спикера) вместо одного, а центроид теперь обновляется всегда при отнесении к спикеру, взвешенно по длительности сегмента (короткая шумная реплика двигает профиль слабо, длинная — сильно); в `app/pipeline.py` сегменты короче 300мс не уходят в Whisper (заодно снимает часть галлюцинаций-на-тишине и их фантомные кластеры, см. запись про "Редактор субтитров..." ниже). Проверено на 4 реальных записях (человек+человек, человек+голос ИИ из динамиков через один микрофон) — везде устойчиво держит верное число реальных участников.
- 2026-09-25 — Stage 3 (захват вкладки + микс с микрофоном) — автотест (Playwright) не смог проверить реальное смешение двух живых источников (ограничение test-инфраструктуры Chromium). — **решено** (2026-09-25): ручной тест в реальном Chrome подтвердил, что звук вкладки (подкаст) и микрофон захватываются и транскрибируются корректно из одного смешанного потока; черновая live-диаризация путается на смеси (ожидаемо, задокументированный компромисс), но фоновая реконсиляция (Stage 4) после звонка верно развела на 2 настоящих голоса. См. `docs/status.md`.
